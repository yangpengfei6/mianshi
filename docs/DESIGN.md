## 1. 我如何理解这道题

题目给了三个交付物，但拆开看考核点是四件事：

| 交付物 | 表面要求 | 我判断的真实考察点 |
|--------|----------|--------------------|
| 单据 DocType | 一张表 + Mock 数据 | **数据建模能力**：字段划分是否合理、能否支撑后续分析、边界约束是否完备 |
| 报表 Report | 展示增长/流失 | **指标口径的严谨性**：流失率的分母是谁、当月没走完怎么办、趋势和下钻能不能用同一份数据集 |
| 大屏 Page | 好看能投屏 | **前后端贯通 + 工程判断**：什么时候该引入第三方库、什么时候不该；投屏场景的特殊性 |
| Git 仓库提交 | 交付代码 | **工程素养**：分层是否清晰、有没有测试、能不能一键装起来跑通 |

题目特意说明"数据格式、报表形式、大屏样式无限制，请自由发挥"——
我把它理解为：**在合理范围内主动展示工程判断力**。
因此本 App 里刻意保留了几处"看起来多余、但其实必要"的设计（单一数据源、口径标注、自动结论），
它们正是面试时可以展开讲的内容。

## 2. 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│  出口层                                                      │
│   Script Report        Desk Page(JSON)       REST API        │
│   user_growth_          growth_screen.js     api/dashboard.py │
│   analytics.py                                               │
└──────────────┬──────────────────┬─────────────────┬──────────┘
               │                  │                 │
               └──────────────────┼─────────────────┘
                                  ▼
                     analytics/service.py   ← 唯一的 ORM 出入口
                                  ▼
                     analytics/core.py      ← 零 Frappe 依赖的引擎
                     ▲          ▲
                     │          │
              pytest（本地）   scripts/make_fixture.py → 前端验证
```

**一条铁律：聚合公式只允许出现在 `analytics/core.py`。**

报表、大屏、API 三条出口都必须经过 `service.py` 调用 core。
这样"报表和大屏数字不一致"这个问题在**架构层面就不可能发生**，
而不是靠人工对比保证。

**为什么 core 要做到零 Frappe 依赖？**

1. 可以被 pytest 直接断言——这是我在无法启动 Frappe 环境的机器上唯一能真正验证代码的方式；
2. 换成数仓 / Frappe Insights 做数据源时，只需替换 service，引擎不动；
3. 指标口径集中在一个文件里，Code Review 时只需要看这一个文件。

## 3. 数据模型设计

### 为什么"开通"和"流失"放在同一张表里？

题目说的是"一份用户服务开通/流失信息单据"。
从分析角度看，流失率、生命周期、LTV 这几个指标**天然需要同一行的开通日期和流失日期**，
拆成两张表就要做 join 和时间对齐，徒增复杂度。
所以采用"一张生命周期主表 + 一张事件流水子表"的结构：

- **主表**：一行 = 一个客户主体的一次服务周期，包含开通与流失两端的信息。
  流失回流的用户会新开一行（保留原 `user_id`），这样既能算"回流率"，也不会污染首次开通的 Cohort。
- **子表**：记录开通 / 续费 / 升级 / 预警 / 流失 / 召回的事件流水。

### 派生字段为什么入库计划而不临时算？

`status`/`lifetime_days`/`ltv`/`risk_score` 都是派生态，全部在 `validate()` 里兜住并落库。
理由：**不能指望录入侧永远正确**。数据导入、API 写入、脚本都可能绕过前端校验，
把规则放在唯一的写入入口，才能保证下游报表不会算出负数生命周期。

- `status` 由「流失日期」这个硬事实推导，状态与日期冲突时**以日期为准**；
- 未来会被 `frappe.throw` 拦住，避免污染当月 Cohort 分析；
- 未流失却残留了流失原因 → 直接清空，否则会混进"流失归因"报表。

### 为什么不启用 Frappe 通用版本追踪？

`track_changes = 0`。通用版本表会把每一次字段微调都记录，
几百条档案反复编辑就会导致版本表膨胀、查询变慢。
改用**专用事件流水子表**，只记录与生命周期强相关的关键跃迁，
既能回答"有多少人流失后被召回"，存储也可控。

## 4. Mock 数据：为什么不用 `random.uniform` 一把梭？

目标是让报表**能讲出可信的业务故事**。如果数据是均匀随机的，
那"渠道质量分析"视图就是一堆彼此差不多的数字，毫无信息量。

所以这里用的是**事件驱动的生存模型**：

```
月度签约数 = 基线 × 复合增长(5.5%/月) × 季节性 × 营销活动脉冲 × 噪声
         ↓
逐月推进流失：hazard = 基线 × 渠道系数 × 套餐系数 × 生命周期系数
```

其中刻意埋了三个真实的业务规律：

1. **早流失期**：前 3 个月磨合期流失最高（系数 1.9），跨过试用期后显著回落（0.4~0.75）；
2. **渠道质量分层**：转介绍最稳、付费广告最差，`hazard` 相差 3 倍以上；
3. **买量扩盘的副作用**：近半年付费广告投放占比抬升，
   导致整体流失率温和抬头——复现真实的"买来的量留不住"。

最终效果（788 条数据）：

| 维度 | 结论 |
|------|------|
| 渠道 | 转介绍流失 11.8% vs 付费广告 46.5%（差 3.9 倍） |
| 套餐 | 免费试用 36.4% vs 旗舰版 11.8% |
| 流失原因 | 价格因素平均存活 115 天；服务支持不足仅 57 天（高价值客户早期流失） |
| 留存 | M6 稳定在 79~82% |

**固定随机种子**（`seed=20261014`）：任何人安装后数据完全一致，便于回归和排障。

## 5. 报表设计

### 为什么做成"多视图"而不是 7 个报表？

增长分析的读者其实是**同一批人在问不同问题**：这个月在涨吗？哪批人留下来了？哪个渠道买来的？
拆成 7 个报表会让人在报表列表里迷路，而且每个报表要重复维护同一套过滤逻辑。
用一个 `view` 参数做路由，共用一条取数链路，是更经济的选择。

### 为什么用 Script Report 而不是 Query Report？

- Cohort 留存矩阵的行列数随观察期**动态变化**，纯 SQL 要把列名拼进字符串，还得自己处理转义；
- 分层聚合（先取全量历史做趋势、再取当期 cohort 做下钻）用 ORM + Python 表达更清晰；
- 与 core 共用逻辑。

### 两条容易被忽略、但代码里显式处理了的口径

**① 趋势与下钻用不同的数据集**

- **趋势**必须基于 `activation_date <= to_date` 的**全量历史**，
  否则"期初活跃"会漏掉更早签约且仍在服的用户，导致数字虚低；
- **下钻**才限定统计区间内的新增 cohort，用于回答"这批人来自哪里"。

这两个口径在报表顶部和页面底部都有明确标注。

**② 当月尚未走完（Partial Month）**

10 月在 14 号这天只过了 45%，新增和流失天然都偏低，
如果不加处理，每个月初看板都会误报"流失暴跌/暴涨"。

处理方式有两层：

- **数据生成侧**：最后一个月按已过天数折算 hazard（`1-(1-p)^(已过天数/总天数)`），
  保证**日均**流失风险与整月一致，否则整月的风险会被压缩进短短几天，
  趋势图末月出现虚假的流失尖峰（这是开发过程中真实出现过、被修掉的缺陷）；
- **展示侧**：`growth_trend()` 输出 `is_partial` 标记，末月用**虚线**渲染并给出文字提示。

## 6. 大屏设计

### 为什么不用 ECharts / Chart.js？

1. **零外部依赖**：大屏常部署在内网或离线环境，CDN 拉不到就直接白屏；
2. **体积与可控性**：需要的图形（折线/柱/环/漏斗）都很基础，
   引入 300KB 的图表库换来的却是完全无法调整的渲染细节；
3. **大屏特殊性**：1920×1080 固定画布 + `transform: scale()` 等比贴合窗口，
   比"自适应容器"更能保证投屏时版式不崩。

全部图表手写成 SVG 字符串函数（`giTrendChart` / `giDonut` / `giColumnChart` / `giBarList` / `giFunnel`），
返回纯字符串，天然免疫 XSS（所有变量统一走 `giEsc()`）。

### 大屏场景特有的几个处理

| 问题 | 处理 |
|------|------|
| 常亮不关，重复轮询压垮数据库 | 60 秒轮询 + **结果缓存 60s** + 页面隐藏（`visibilitychange`）时暂停，回到前台立即补一次 |
| 会议室没人看时也在查 | 同上，分母级优化 |
| Page 路由本身不做权限隔离 | 真正的校验放在数据接口层 `api/dashboard.py` |
| 看不到"所以呢" | 后端 `core.derive_insights()` 直接算出结论条目，例如"付费广告流失率是转介绍的 3.9 倍，建议下调投放占比" |
| 安装后不知道从哪进 | 报表里内置跳转按钮；路由 `/app/growth-screen` |

### 静态预览 `docs/preview.html`

因为在无法起 Frappe 环境的条件下无法截图，这里额外做了一个预览页生成器
`scripts/make_preview.js`：**直接抽取 `growth_screen.js` 里的同一批渲染函数**，
用真实数据拼出 HTML。因为函数、CSS、布局常量都是同一份代码，
预览页与线上页面不存在"预览好看、线上错位"的问题。

## 8. 设计决策记录（DR）

> 面试时讲"我选了 A 而没选 B，代价是 C"，比讲"我用了 A"有力得多。

### D1. 多视图报表 vs 拆分多个报表
- **选**：一份报表 + `view` 参数路由
- **弃**：7 个独立报表
- **理由**：同一批读者的不同提问；过滤逻辑只需维护一份
- **代价**：单个文件的 columns 分支略多，用 `GrowthReport` 类 + handler 映射收敛

### D2. Script Report vs Query Report
- **选**：Script Report
- **弃**：纯 SQL Query Report
- **理由**：Cohort 矩阵行列动态、分层聚合表达力、与 core 共用口径
- **代价**：数据量到十万级以后性能不如 SQL，届时应改为 Insights 或物化表

### D3. 手写 SVG vs 引入 ECharts
- **选**：手写
- **弃**：CDN / npm 图表库
- **理由**：内网可用、零构建、细节可控
- **代价**：tooltip、缩放等交互需要自己实现；大屏本身也不需要鼠标交互，代价可接受

### D4. 专用事件子表 vs 通用版本追踪
- **选**：专用子表 + `track_changes=0`
- **理由**：版本表会记录所有字段微调，存储爆炸且查询变慢
- **代价**：非结构化字段的修改历史不再可追溯（对本题场景可接受）

### D5. Controller `autoname()` vs DocType `format:` 规则
- **选**：Controller 方法
- **理由**：Frappe **v16 已废弃**旧式花括号占位符（`{MM}`），写成方法可 v14~v16 通吃，且能自定义年月前缀
- **代价**：多了十几行代码

### D6. 不随 App 发布 Workspace fixture
- **选**：不打包，改为路由访问 + 报表内跳转
- **理由**：Workspace 的 `content` 是 JSON-in-JSON，各版本卡片/区块结构仍在演进；
  一旦与目标版本不匹配，**会让整个安装流程报错**，收益（入口更好看）远小于风险
- **代价**：用户需要记住 `/app/growth-screen` 这个路由（README 已写明）
- **何时改回来**：等 Workspace schema 稳定、或明确目标只有 v16 时，用 UI 配好再导出为 fixture

### D7. 自定义角色 + `before_install` 提前创建
- **选**：DocType JSON 里直接声明自定义角色权限，并在 `before_install` 先把角色建好
- **理由**：Frappe 安装顺序是 `before_install` → 同步 DocType，这样恰好赶在权限表落地前准备好
- **代价**：依赖安装内部顺序（如果框架改动顺序，行为会受影响，因此 `after_migrate` 也补一次）

### D8. 核心引擎零 Frappe 依赖
- **选**：抽出 pure-Python core
- **理由**：可测试、可替换、口径集中；也是我在无数据库环境下唯一能真正验证逻辑的方式
- **代价**：多了一层 service 转换

### D9. 缓存 + 页面隐藏暂停轮询
- **选**：60s TTL 缓存 + `visibilitychange` 暂停
- **理由**：大屏常年在会议室开着，多个查看者很容易把数据库压垮
- **代价**：数据最多延迟 60s（大屏场景可接受，且页面底部显示倒计时）

## 9. 开发过程中发现并修掉的真实缺陷

> 这一节建议直接讲——它证明你真的跑过代码，而不是写完就交。

| # | 缺陷 | 怎么发现的 | 修法 |
|---|------|-----------|------|
| 1 | **末月流失密度虚高**：10 月只到 14 号，却按整月 hazard 计算，趋势图末柱出现假的流失尖峰（3.8% vs 上月 2.4%） | 打印月度趋势逐行核对 | hazard 按已过天数折算，保证日均风险一致；同时加 `is_partial` 标记 + 虚线渲染 |
| 2 | **漏斗不单调**："付费用户 73.9%" 排在 "当前在服 75.3%" 之后，漏斗出现"回升"的荒谬形状 | 打印漏斗四层数值 | 重定义为 累计开通 → 当前在服 → **付费在服** → 长期留存，严格递减 |
| 3 | **回流类型污染**：26 条"流失回流"里只有 8 条是真的，其余是随机权重让全新用户被标成回流 | 单元测试断言 user_id 复用 | "流失回流"从普通签约权重中移除，只由回流流程产生 |
| 4 | **活跃记录残留流失原因**：未流失的用户带着 `churn_reason` | 单元测试断言归因结果集 | `normalize_records` 统一清空 |
| 5 | **月份差 off-by-one**：用 `days // 30` 近似月份差，跨月时出错 | code review | 新增 `month_diff()` 用日历月份精确计算 |
| 6 | **v16 命名规则废弃**：`format:{MM}` 在 v16 已 deprecated | 查阅官方 Naming 文档 | 改用 Controller `autoname()` |
| 7 | **未知权限字段**：`export` 权限在部分版本不存在，写入 DocPerm 会报错 | 主动排查 | 从 DocType JSON 中移除，只保留通用权限位 |
| 8 | **分布 MRR 语义混淆**：生命周期分布把流失用户的 MRR 也算进当期收入 | 检查输出字典 | 拆成 `mrr`（在服）与 `lost_mrr`（已流失） |

## 10. 没有 Frappe 环境，如何保证代码能跑？

这台机器没有 Docker / WSL，无法拉起 Frappe + MariaDB。我的应对策略：

1. **把核心逻辑做成零依赖**，让最关键的 80% 能被 pytest 真实断言（59 项测试通过）；
2. **把手写的图表渲染函数做成纯函数**，用 Node + vm 沙箱注入真实数据跑一遍，
   专门检查 SVG 里出现 `NaN`/`undefined`、标签不配对这类致命问题；
3. **写仓库自检脚本**，用 AST 检查那些"只有装到 Frappe 里才会暴露"的不一致
   （JSON 与 .py 不同步、Select 选项与 constants 不一致、hooks 路径指向不存在的函数等）；
4. **逐项核实版本差异**（Naming 规则、权限字段、page JS 加载机制、Workspace schema），
   而不是凭印象写。

诚实的边界：**DocType 落库、Report 在 Desk 里的实际渲染、Page 的加载**这三项
未经真机验证，需要 `bench install-app` 后才能确认。已完成的一切等待命中的快速验证清单见 README §六。

## 11. 预判提问 Q&A

**Q：流失率的分母为什么是"期初活跃"而不是"本月总用户"？**
> 这是 SaaS 的标准算法：流失率衡量的是"月初还在的人里，有多少人在这个月没了"。
> 用总用户做分母会把当月新签但还没来得及流失的人稀释进去，导致流失率被低估。
> 代码里 `opening_active` 是独立算出来的，且有单测保证"期初 + 新增 − 流失 = 期末"这条恒等式。

**Q：当月没走完的数据怎么处理？**
> 两个层面：数据侧按日均折算避免假尖峰（并且这是我在开发中真实修掉的 bug），
> 展示侧用 `is_partial` 标记 + 虚线 + 文字提示。真实场景里很多人直接拿部分月和整月横向比，
> 结果每个月初都报警。

**Q：数据量上来以后怎么办？**
> 现在全量取到 Python 侧聚合，几百到几千条没问题。
> 十万级以上应该改成：SQL 窗口函数算 cohort、或者接入 Frappe Insights；
> 由于 core 是纯函数，改造时只需替换 service 层的取数方式，上层三条出口不用动。

**Q：为什么 Report 和大屏的数字一定一致？**
> 因为它们在架构上就必须走同一个 `analytics/core.py`。
> 我特意把"聚合公式只允许出现在 core"当成一条铁律写进了文档的 module docstring，
> 并且用 `scripts/validate_repo.py` 做护栏，防止后续改动破坏这条约束。

**Q：为什么不用 ECharts？**
> 三句话：内网环境 CDN 拉不到会白屏；需要的图形很基础，引 300KB 库不划算；
> 大屏是投屏场景不需要鼠标交互，反而要精确的版式控制。
> 代价我清楚——交互要自己实现，这里做了取舍。

**Q：Mock 数据为什么不干脆随机？**
> 随机会让"渠道质量分析""套餐表现"这些视图变成一堆没有区分度的数字。
> 我用的是生存模型 + 渠道/套餐/生命周期三类系数，刻意埋了"买量用户质量差"这个真实规律，
> 报表才能讲出"付费广告流失率是转介绍的 3.9 倍"这种能落地的结论。

**Q：权限怎么控制的？大屏谁能看？**
> App 自带 `Growth Analyst`（读写）和 `Growth Viewer`（只读）两个角色。
> 但关键是：Frappe 的 Desk Page 路由**本身不做角色隔离**，任何登录用户都能敲 URL。
> 所以真正的拦截放在了数据接口层 `api/dashboard.py` 的 `_ensure_permission()`。

**Q：子表流水和版本追踪重复吗？**
> 不重复，恰恰是为了替代它。版本表记录所有字段微调，几百条档案反复编辑就会爆；
> 这里只用一张专用子表记关键跃迁，存得少、查得快、语义也清楚。

**Q：区域分布为什么没做中国地图？**
> 一是 GeoJSON 体积大且涉及地图数据合规；二是大屏距离远，地图上的色块看不清，
> 横向条形榜反而更直观可读。区域维度用 Top8 条形即可回答"哪块占比最大"。

**Q：如果线上发现拓 Toy Chicken Fieldüz需要改，怎么迁移？**
> 新增字段直接改 JSON，`bench migrate` 会自动同步；
> 需要数据回填的场景写 `patches.txt` 里的 patch（`patches/` 目录已预留）。
> 破坏性结构变更则要拆到 major 版本。

**Q：为什么不用 fixtures 导出 Mock 数据？**
> fixtures 是静态 JSON，既难以表达"随机但服从合理分布"这件事，
> 也无法保证多次生成结果一致。程序化生成可以随时调参数、保证可复现，
> 还能被单测断言分布特征（比如"各渠道流失率必须有明显分层"）。

**Q：满足了"24 小时"和"本人完成"吗？**
> 代码全部由本人编写，AI 用于框架版本差异核查与方案讨论（题目明确允许）。

## 12. 还能做什么（Roadmap）

- **成本续约**：接入真实活跃埋点后，把 `risk_score` 换成 ML 流失预测（现为经验阈值）

- **脱离单一数据源**：支持把数据源切到数仓（只需替换 `service` 层，引擎不动）
